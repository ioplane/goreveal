# SIMD и максимальная утилизация CPU в Go-проектах реверс-инжиниринга

**Go не выполняет автовекторизацию, но экосистема предлагает мощные альтернативы: от avo-генерируемого ассемблера до экспериментального пакета `simd/archsimd` в Go 1.26, способного ускорить код в 16 раз по сравнению со скалярными циклами.** Для проекта GoReveal, парсящего Go-бинарники размером 50–200+ МБ, комбинация mmap-доступа к файлу, SIMD-ускоренного сканирования паттернов, SoA-раскладки данных и параллельного анализа функций способна сократить время полного анализа бинарника до **50–100 мс** на современном 8-ядерном процессоре. Данный отчёт охватывает все ключевые направления: от состояния SIMD в Go до конкретных архитектурных решений для RE-инструмента.

---

## Компилятор Go и SIMD: что есть сейчас и что появится завтра

Компилятор `gc` **не выполняет автовекторизацию циклов** — это осознанный компромисс в пользу скорости компиляции. В отличие от GCC/Clang с `-O3 -ftree-vectorize`, SSA-бэкенд Go выполняет только скалярные оптимизации: устранение bounds check, constant propagation, dead code elimination. Численный код на Go типично работает в **1.5–2× медленнее** эквивалентного C/C++ с полной векторизацией.

**Go 1.26 (февраль 2026)** приносит революционное изменение — экспериментальный пакет `simd/archsimd` под флагом `GOEXPERIMENT=simd`. Это архитектурно-специфичные SIMD-интринсики для AMD64, компилируемые в одиночные инструкции. Ключевое преимущество — **инлайнинг**: в отличие от `.s`-файлов, вызовы `simd/archsimd` встраиваются в вызывающий код, поддерживают асинхронную преемптивность горутин и не требуют ручного ассемблера. Ранние бенчмарки показывают, что инлайн-SIMD через этот пакет **в 4× быстрее avo-генерированного ассемблера** и **в 16× быстрее скалярных Go-циклов** для операций типа сложения 32 элементов `uint8`. Пакет реализует двухуровневый подход: низкоуровневый `simd/archsimd` (доступен сейчас для AMD64) и высокоуровневый портативный API (планируется в будущих версиях).

Флаги `GOAMD64` (введены в Go 1.18) определяют минимальный уровень микроархитектуры: **v1** (SSE2, по умолчанию), **v2** (SSE4.2, POPCNT — ускоряет `math/bits.OnesCount`), **v3** (AVX2, FMA — ускоряет `math.FMA`, добавляет BMI1/BMI2, LZCNT), **v4** (AVX-512 — зарегистрирован, но компилятор **не генерирует AVX-512 инструкций**). Для GoReveal рекомендуется сборка с `GOAMD64=v3` — это охватывает все процессоры с 2013 года (Intel Haswell, AMD Ryzen) и даёт ощутимый прирост в математических операциях и битовых манипуляциях.

## Инструментарий: avo, Plan 9 asm и стратегия выбора

**avo** (github.com/mmcloughlin/avo) — главный инструмент для написания SIMD на Go. Это генератор x86-ассемблера, написанный на Go: вы описываете SIMD-операции через Go API, `go generate` создаёт `.s`-файлы и Go-заглушки. Avo поддерживает полный набор инструкций: SSE через AVX-512, AES-NI, CLMUL, FMA, VNNI. Виртуальная аллокация регистров, автоматическое управление стековым фреймом, Go-подобный control flow. Проект используется в продакшене: **klauspost/reedsolomon**, **cloudflare/circl**, **zeebo/xxh3**, **minio/md5-simd**, и даже сам `crypto/` пакет Go stdlib содержит avo-генерированный ассемблер.

**Критическое ограничение avo**: ассемблерные функции из `.s`-файлов **не инлайнятся** компилятором Go. Каждый вызов стоит ~10–20 нс. Это означает, что SIMD-функция должна обрабатывать минимум **256 байт–1 КБ** за вызов, чтобы overhead окупился. Для GoReveal это не проблема — типичные операции (сканирование секции, хеширование функции) работают с блоками от 100 байт до десятков килобайт.

**Иерархия подходов** (от лучшего к худшему):

1. **`simd/archsimd` (Go 1.26+)** — инлайнится, безопасен, нативен. Экспериментален, но официально поддерживается
2. **avo-генерированный ассемблер** — проверен в продакшене, cross-compilation работает, не требует CGo
3. **Ручной Plan 9 asm** — те же преимущества, что у avo, но сложнее писать и поддерживать
4. **CGo с C SIMD-интринсиками** — overhead ~38–40 нс за вызов (Go 1.21), ломает cross-compilation, оправдан только для обёрток больших C-библиотек с длительными операциями (>1 мкс)

Для рантайм-детекции CPU-фич используйте `golang.org/x/sys/cpu` (публичный API) или `github.com/klauspost/cpuid/v2` (расширенная детекция с размерами кешей). Паттерн диспатча прост:

```go
var scanFunc func([]byte, []byte) int
func init() {
    if cpu.X86.HasAVX2 { scanFunc = scanAVX2 }
    else { scanFunc = scanGeneric }
}
```

## Конкретные SIMD-оптимизации для парсинга Go-бинарников

### Сканирование magic bytes и паттернов

Поиск magic bytes pclntab (`0xFFFFFFFA`, `0xFFFFFFF0` и т.д.) в 200-мегабайтном файле — идеальная задача для SIMD. **Три подхода по возрастанию сложности:**

**Подход 1 — `bytes.Index`**: уже SIMD-ускорен в Go runtime. Реализация `runtime·indexbytebody` использует SSE2-инструкции (PCMPEQB + PMOVMSKB), обрабатывая **16 байт за такт**. Для 4-байтного паттерна `bytes.Index(data, magic)` — разумный стартовый выбор. На ARM64 аналогично используется NEON.

**Подход 2 — Кастомный AVX2-сканер через avo**: загрузка 32 байт через `VMOVDQU`, broadcast 4-байтного magic через `VPBROADCASTD`, сравнение через `VPCMPEQD`, извлечение маски через `VPMOVMSKB`. Обрабатывает **8 потенциальных совпадений за инструкцию**. Ожидаемая пропускная способность: **10–20 ГБ/с**, что означает полное сканирование 200 МБ файла за **10–20 мс**.

**Подход 3 — Параллельное chunk-сканирование**: разделение файла на overlapping chunks (overlap = `len(pattern) - 1`) с параллельной обработкой через `errgroup.SetLimit(runtime.GOMAXPROCS(0))`. С 8 ядрами — **2–5 мс** на 200 МБ.

### Хеширование функций для fingerprinting

Для fingerprinting ~50K функций (GoResolver-подобный функционал) **SHA-256 — overkill**. Сравнение хеш-библиотек:

| Библиотека | Пропускная способность | Разрядность | Рекомендация |
|---|---|---|---|
| **hash/crc32** (stdlib, SSE4.2) | 10–13 ГБ/с | 32-bit | Быстро, но коллизии при 50K элементах (~0.03%) |
| **cespare/xxhash/v2** (XXH64, asm) | 10–13 ГБ/с | 64-bit | Оптимальный баланс скорости и надёжности |
| **zeebo/xxh3** (XXH3) | 10–30+ ГБ/с | 64/128-bit | Максимальная скорость, SIMD-friendly дизайн |
| **minio/sha256-simd** (AVX2) | ~450 МБ/с | 256-bit | Только если нужна криптостойкость |

**Рекомендация**: **cespare/xxhash/v2** для простоты или **zeebo/xxh3** (128-bit) для минимального риска коллизий. При средней длине функции 1 КБ и 50K функций (50 МБ данных), хеширование займёт **~5 мс** — пренебрежимо мало.

### JSON-сериализация результатов анализа

Для сериализации 50K+ записей о функциях:

| Библиотека | Encode | Decode | Ускорение vs stdlib | API-совместимость |
|---|---|---|---|---|
| **encoding/json** | ✅ | ✅ | 1× | — |
| **goccy/go-json** | ✅ | ✅ | 2–3× encode/decode | Drop-in замена |
| **simdjson-go** | ❌ | ✅ | **5–16× decode** | Свой API |
| **bytedance/sonic** | ✅ | ✅ | 2–4× (JIT+SIMD) | Частичная |

**Практическая оценка**: 50K записей × ~500 байт ≈ 25 МБ JSON. С goccy/go-json (~300 МБ/с encode): **~80 мс**. С simdjson-go для декодирования: **~25 мс**. Для внутреннего кеширования между запусками анализа рассмотрите бинарные форматы (Protocol Buffers, FlatBuffers) — **в 10–50× быстрее** JSON.

## Стратегия работы с памятью: mmap, кеш-линии и параллелизм

### mmap как фундамент для RE-инструмента

Memory-mapped I/O — **безусловный выбор** для парсинга бинарников. Бенчмарки показывают: **3.3 нс** за random lookup через mmap против **416 нс** через `pread` — разница в **126×**. Для 200-мегабайтного файла на системе с 8+ ГБ RAM файл гарантированно помещается в page cache.

```go
data, _ := mmap.Map(f, mmap.RDONLY, 0) // zero-copy доступ
defer data.Unmap()
elfHeader := data[0:64] // прямой слайс, без копирования
```

**Критический нюанс** (из опыта VictoriaMetrics): горутины **не блокируются и не уступают** при major page fault на cold mmap-данных. Все GOMAXPROCS потоков могут застрять в page fault одновременно. Решения: (1) pre-fault страниц последовательным чтением перед параллельной обработкой, (2) `madvise(MADV_WILLNEED)`, (3) `mmap.Lock()` для закрепления страниц. Для GoReveal при первом открытии файла выполните последовательный проход по всем страницам — это заполнит page cache и TLB за **~10–50 мс**.

### SoA-раскладка для таблиц функций

Struct of Arrays **в 12.7× быстрее** Array of Structs, когда вы обращаетесь к малой доле полей большой структуры — именно такой паттерн при сканировании pclntab:

```go
// ❌ AoS — при сканировании Entry загружаем все холодные данные
type FuncInfo struct {
    Entry     uint64   // HOT при сканировании
    Name      string   // COLD
    FrameSize int32
    PCSP      []byte   // COLD
}

// ✅ SoA — сканирование Entries: 8 записей на кеш-линию
type FuncTable struct {
    Entries    []uint64  // HOT: непрерывное сканирование
    FrameSizes []int32   // Warm: фаза анализа
    Names      []string  // COLD: только для вывода
    PCSP       [][]byte  // COLD: по запросу
}
```

При 64-байтной кеш-линии x86-64 и 8-байтных `uint64` адресах — **8 записей функций на кеш-линию** в SoA против **1 записи в AoS** при 100-байтной структуре. Для таблицы из 50K функций это разница между **50K/8 ≈ 6250 cache misses** и **50K cache misses**.

**Упорядочение полей в структурах**: Go не переставляет поля автоматически. Располагайте поля от большего к меньшему для минимизации padding: `int64` → `int32` → `bool`. Разница может составлять 30–50% размера структуры (пример: 24 байта vs 16 байт при 3 полях).

### Параллельный анализ: двухфазный подход

Оптимальная архитектура для GoReveal:

**Фаза 1 (последовательная, быстрая):** парсинг ELF/PE/Mach-O заголовков, локализация секций, построение таблицы функций из pclntab. Это ~1–5 мс работы, не стоит параллелить.

**Фаза 2 (параллельная):** fan-out анализа функций через `errgroup.SetLimit(runtime.GOMAXPROCS(0))`. Каждая горутина получает слайс mmap-данных `data[fn.Start:fn.End]` и выполняет независимый анализ. Результаты записываются в pre-allocated массив `results[i]` — каждый `i` на отдельной кеш-линии, исключая false sharing.

**False sharing** — реальная угроза при параллельной записи. Две переменные на одной 64-байтной кеш-линии, модифицируемые разными ядрами, вызывают cache line bouncing. Padding с `[56]byte` между конкурентными полями даёт **6.4× ускорение** под контрой. Go runtime учитывает это в `sync.Pool` (padding `poolLocal` до 128 байт). Для GoReveal используйте per-goroutine аккумуляторы с финальным merge:

```go
results := make([]FuncAnalysis, len(funcs)) // Pre-allocated, indexed by task
g.SetLimit(runtime.GOMAXPROCS(0))
for i, fn := range funcs {
    g.Go(func() error {
        results[i] = analyzeFunction(data[fn.Start:fn.End]) // Нет разделяемого состояния
        return nil
    })
}
```

## ARM64: NEON как единственный практичный путь

На ARM64 Go поддерживает только **NEON** (ASIMD) — фиксированные 128-битные вектора. SVE/SVE2 **не поддерживаются ассемблером Go** и не имеют предложений по реализации. Apple Silicon (M1–M4) **не реализует SVE/SVE2**, что делает инвестиции в SVE неоправданными для кросс-платформенного инструмента.

NEON-регистры доступны как `V0`–`V31` в Plan 9 asm с arrangement specifiers: `V0.B16` (16 байт), `V0.S4` (4 words), `V0.D2` (2 doublewords). Go stdlib активно использует NEON: `crypto/aes` (инструкции AESE/AESD — **93% ускорение**), `crypto/sha256` (SHA256H/SHA256H2), `hash/crc32` (аппаратный CRC32), `runtime.memmove` (VLD1/VST1), `bytes.IndexByte` (NEON-сканирование). Библиотека `minio/sha256-simd` демонстрирует **105× ускорение** на ARM64 Crypto Extensions vs pure Go.

**Кросс-платформенная организация кода:**

```
pkg/
├── scan.go              # Интерфейс + pure Go fallback
├── scan_amd64.go        # x86 feature detection + Go wrappers
├── scan_amd64.s         # SSE2/AVX2 assembly (через avo)
├── scan_arm64.go        # ARM64 feature detection
├── scan_arm64.s         # NEON assembly (ручной)
└── scan_generic.go      # //go:build !amd64 && !arm64
```

Для ARM64 ассемблера нет эквивалента avo — приходится писать вручную или использовать `gorse-io/goat` (компилирует C с SIMD-интринсиками в Go-ассемблер, поддерживает NEON). Флаг `GOARM64=v8.2,crypto` для таргетинга Apple M1+ и Graviton2+ позволяет компилятору пропускать runtime-проверки crypto extensions.

**Apple Silicon специфика**: унифицированная архитектура памяти (UMA) с пропускной способностью **68–120 ГБ/с** (M1→M4). Go scheduler **не различает P-cores и E-cores** — это делает ОС. Все M-чипы гарантируют NEON, AES, SHA2, CRC32, LSE atomics.

## Экосистема SIMD-библиотек: что использовать в GoReveal

### Обязательные зависимости

- **klauspost/cpuid/v2** — детекция CPU-фич, инлайнится, поддерживает все x86 и ARM фичи. Быстрый путь через `CPU.HasAll(features)`
- **cespare/xxhash/v2** — XXH64 хеширование для fingerprinting функций, assembly-оптимизирован для amd64 и arm64, **10–13 ГБ/с**
- **goccy/go-json** — drop-in замена encoding/json, **2–3× ускорение** без SIMD, чистый Go
- **klauspost/compress/zstd** — для сжатия результатов анализа, assembly-декомпрессия **2× быстрее** pure Go

### Опциональные для максимальной производительности

- **minio/simdjson-go** — **10× быстрее encoding/json** при декодировании, требует AVX2+CLMUL. Stage 1 (SIMD-детекция структурных символов) и Stage 2 (построение tape) работают конкурентно через горутины
- **zeebo/xxh3** — XXH3-128 для 128-битных хешей с минимальным риском коллизий, SIMD-friendly дизайн
- **minio/sha256-simd** — если нужен SHA-256 (совместимость с внешними системами), **AVX-512 даёт 7.8× ускорение** при параллельном хешировании 16 потоков

### Паттерн из klauspost/compress — золотой стандарт организации

Отдельные `.s`-файлы для каждой архитектуры, build-tagged Go-заглушки, tag `noasm` для отключения всего ассемблера, всегда есть pure Go fallback. S2-кодек достигает **>10 ГБ/с** декомпрессии с AMD64 ассемблером.

## Бенчмаркинг и профилирование: как измерять правильно

### Методология измерений

Используйте `testing.B.Loop()` (Go 1.24+), который автоматически предотвращает dead-code elimination. Для sweep по размерам данных — sub-benchmarks с `b.SetBytes()` для автоматического отчёта в МБ/с:

```go
sizes := []int{64, 256, 1024, 4096, 65536, 1<<20}
for _, size := range sizes {
    b.Run(fmt.Sprintf("simd/%d", size), func(b *testing.B) {
        b.SetBytes(int64(size))
        for b.Loop() { simdScan(data[:size]) }
    })
}
```

Запуск: `go test -bench=. -benchmem -count=10 -benchtime=3s`, анализ: `benchstat old.txt new.txt`. Стабильность: отключите frequency scaling (`performance` governor), турбобуст, фоновые процессы.

### Верификация SIMD-инструкций

```bash
go build -o binary . && go tool objdump -S -gnu binary | grep -i 'vmov\|vpadd\|vpshuf\|vpcmp'
```

На Linux `perf stat -e instructions,cycles,fp_arith_inst_retired.256b_packed_single ./binary` покажет количество SIMD-инструкций. `perf annotate` отображает hotspot на уровне инструкций. AMD uProf способен показать распределение AVX-512 vs AVX2 vs SSE vs scalar.

**pprof** показывает, какие функции горячие, но **не различает скалярные и SIMD-инструкции** внутри функции. Для ассемблерных функций из `.s`-файлов pprof показывает время в функции, но не даёт line-level аннотации внутри ассемблера.

### Когда SIMD оправдан: точка пересечения

Минимальный размер данных для выигрыша от SIMD:
- **С инлайн-SIMD (`simd/archsimd`)**: от **32–64 байт** — overhead минимален
- **С avo/.s ассемблером**: от **256 байт–1 КБ** — нужно амортизировать ~10–20 нс вызова
- **С CGo**: от **10 КБ+** — нужно амортизировать ~40 нс overhead

Для GoReveal все типичные операции (сканирование секции: КБ–МБ, хеширование функции: 100 Б–10 КБ, JSON: МБ) **превышают порог**, SIMD оправдан.

### Ограничение памятью, а не вычислениями

**Критический факт**: простые операции сканирования байт с SIMD достигают **30–50 ГБ/с на ядро**, упираясь в пропускную способность DDR4/DDR5 (**25–50 ГБ/с на канал**, dual-channel даёт 50–100 ГБ/с). При таких скоростях 200 МБ сканируются за **4–10 мс** одним ядром. Многопоточность даёт линейное масштабирование **до насыщения шины памяти**. Вычислительно-тяжёлые операции (SHA-256, zstd-сжатие) остаются compute-bound и масштабируются лучше.

## Итоговая архитектура для GoReveal

**Фундамент**: mmap всего файла → pre-fault последовательным чтением → двухфазный анализ.

**Фаза 1** (последовательная, ~5 мс): ELF/PE/Mach-O парсинг заголовков, поиск pclntab magic через `bytes.Index` (SSE-ускоренный в runtime), построение SoA-таблицы функций.

**Фаза 2** (параллельная, ~20–50 мс): `errgroup` с `SetLimit(GOMAXPROCS)`, каждая горутина анализирует одну функцию из mmap-данных, fingerprint через `cespare/xxhash/v2`, результаты в pre-allocated `results[i]`.

**Сериализация** (~80 мс): `goccy/go-json` для JSON-вывода; бинарный кеш (gob/protobuf) для повторных запусков.

**Приоритет оптимизаций** (от высшего к низшему):

1. Алгоритмические улучшения и SoA-раскладка данных — **10–100× потенциал**, минимальная сложность
2. mmap + параллельный анализ через `errgroup` — **4–8× на многоядерной системе**, стандартный Go
3. `bytes.Index` для паттерн-сканирования — **уже SIMD-ускорен**, нулевая сложность
4. Замена encoding/json на goccy/go-json — **2–3×**, одна строка `import`
5. xxHash для fingerprinting вместо SHA-256 — **20–100×**, тривиальная замена
6. Кастомный AVX2-сканер через avo — **2–5×** сверх `bytes.Index`, высокая сложность
7. `simd/archsimd` (Go 1.26) — **4–16×** для точечных операций, экспериментален

Для зрелого проекта пункты 1–5 дадут **90% возможного ускорения** при минимальных затратах. SIMD-ассемблер (пункты 6–7) оправдан только после того, как профилирование покажет конкретный bottleneck в compute-bound операции на данных размером >1 КБ.
